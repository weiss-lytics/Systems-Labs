Project Brief

Shiori — One task at a time.

A private, single-file kanban board for people who feel worn down by loud productivity apps — dense grids, streak guilt, notification badges. Shiori asks one question, quietly: what should you work on next?

Core Philosophy

"Peaceful over powerful — the interface should never compete for attention with the work itself."

Target Users

Solo, focused individuals who want a calm personal task tool — no accounts, no sync, no one else looking at their board. People who've bounced off Notion-style complexity and just want to know what's next.

What makes it different
Fully local — no login, no server
One file, opens by double-click
A "next action" field per task
Motion used only where it means something

Greeting + progress ring, not a table of numbers. One glance should feel like "okay, here's my day" — not a report to read.
Six small cards, same size, same weight. No card is allowed to dominate — that would turn calm into urgency.
UX rationale Why a ring instead of a percentage bar or checklist? ▸
A circular ring reads as "a day, in progress" rather than "a bar to fill and finish." It never implies you're behind — it just quietly shows where you are. Paired with a single rotating motto instead of tips or streaks, so there's no gamification pressure.

One field. That's it. Title only — everything else (priority, tags, due date) can be added later, in the task panel, once the thought has a home.
Three ways in (shortcut, topbar button, per-column button) because capture moments happen at different points in the flow — don't make the user hunt for the one true "add" button.
UX rationale Why minimize fields at capture time? ▸
Every required field at the moment of capture is a chance to lose the thought entirely. Shiori treats "getting it out of your head" and "organizing it" as two separate jobs, done at two separate times — quick add never asks for more than a title.

Priority shown as a thin left-edge color, not a colored badge or icon cluster. It's readable at a glance but never louder than the title.
UX rationale Why seven columns instead of three? ▸
Real work isn't binary (to-do / done). Waiting and On Hold exist so tasks blocked by someone else, or intentionally paused, don't sit guiltily in "In Progress" — reducing the cognitive load of "why hasn't this moved."

Slides in from the side so the board stays visible behind it — you never lose your place in the bigger picture while editing one task.
History is a quiet timeline, not an audit log. It exists so future-you can answer "wait, what did I already try here?" in one glance.
UX rationale Why "next action" as its own field? ▸
The hardest part of returning to a stalled task is rarely the whole task — it's remembering the very next step. A dedicated field means future-you never has to re-derive it.

The Task Lifecycle Blueprint

The centerpiece of the product: how a single task moves through the system, and what state it carries with it at every stage.

waiting / on hold
✅ Done
+history entry, archived
Every node the task passes through adds state — it never loses what came before. By the time it's "Done," its history tells the whole story without you writing a report.
The dashed, branching path (not a straight line) is intentional: tasks don't always move forward in a line — "Blocked?" is a real, honest detour, not a failure state.
UX rationale Why show this as a blueprint, not a flowchart with rules? ▸
There are no enforced transitions in Shiori — any task can move to any column at any time. This diagram documents the *typical* path, not a locked state machine, because real task work resists being locked into rules.
Screen 06 · System

System Architecture

Purpose: show how little architecture this product actually needs — that's the point. No servers, no accounts, no sync layer to fail.

1
User
Opens shiori.html directly in a browser — no install, no account, no URL to remember.
2
Frontend Experience
Dashboard, Board, Notes, Archive, Settings — all rendered client-side, vanilla HTML/CSS/JS, zero build step.
3
Core Processing
In-memory task/note objects — filtering, search, drag-and-drop reordering, checklist progress, all computed instantly in the browser.
4
Transformation Layer
Every change is serialized to a single JSON blob representing the whole app's state.
5
Output Generation
Re-renders affected views (board, dashboard, notes) — cheap, targeted DOM updates, no framework diffing needed at this scale.
6
Storage / Sharing
Persists to the browser's localStorage automatically. Manual JSON export/import is the only "sync" — by design, not limitation.
No backend box on this diagram isn't an omission — it's the whole pitch. Nothing here can go down, get breached, or start charging a subscription.
Export/Import stands in for "sync" and "backup" at once — one honest mechanism instead of two systems pretending to be automatic.
