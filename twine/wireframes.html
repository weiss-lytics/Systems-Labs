Project type
Browser-based meeting time planner for distributed teams and friends
Core problem
Timezone math and Daylight Saving Time create confusion, errors, and missed meetings

Why warmth reduces friction
Timezone tools tend to feel like spreadsheets. A "Good morning" greeting and soft language make the first five seconds feel human, which lowers the guard people bring to anything that sounds technical.

No technical language, ever
You'll never see "UTC+8" on this screen. People think in city names and "morning" or "evening" — not offsets. Twine translates internally so the user never has to.

Recent cities save repeat work
Most people coordinate with the same handful of people repeatedly. Surfacing recent cities turns a 3-step setup into a single tap for returning use cases.

Why visual simplicity matters
Three fields, three taps. Anything more starts to feel like configuring software rather than planning a chat with a friend or colleague.

Dropdowns over manual input
Letting someone type "GMT-5" invites errors and assumes knowledge they may not have. A searchable city dropdown removes the chance of picking the wrong offset entirely.
tap to collapse
DST handling must be invisible
Daylight Saving shifts are the single biggest source of timezone mistakes. Twine resolves this automatically using the city's real timezone rules — the user never sees a DST toggle because they should never have to think about it.

Recommendations — the answer, not the data

Twine never shows two raw clocks and asks the user to do the math. It does the math, then presents a verdict.

Recommendation-first reduces cognitive load
Leading with "We found a great time" instead of a raw comparison table means the user's first read is the conclusion, not the inputs. They can dig deeper if curious, but they don't have to.
tap to collapse
Users shouldn't do timezone math
That's the entire reason this product exists. If someone still has to mentally convert 10 PM Manila to 7 AM Buenos Aires themselves, Twine has failed at its one job.
tap to collapse
Tiered labels over raw scores
"Pretty Good" and "A little late" communicate quality instantly. A numeric overlap score (like "73% overlap") would be more precise and far less useful at a glance.
tap to collapse
Screen 04 / 07

Timeline — support, not spotlight

For users who want to see why a time was recommended, a simple horizontal timeline shows working hours and overlap — nothing more technical than that.

🇦🇷 BA

Timeline exists to support decisions
It's not the hero of the product — the recommendation is. This view is one tap deeper, for the minority of users who want to see the "why" behind the suggested time.
tap to collapse
It should never dominate the interface
No gridlines for every hour, no timezone offset labels, no 24-hour clock notation. Three soft bands — morning, afternoon, evening — keep this readable at a glance.
tap to collapse
Avoid technical visualizations
No Gantt charts, no dual-axis graphs. Two stacked bars and an overlap strip communicate the entire idea without requiring any chart literacy from the user.

Why mobile-first was non-negotiable
Nobody opens a laptop to ask "what time is it for you?" — that question gets typed into a phone, mid-conversation, in seconds. The product has to be fast there first.
tap to collapse
Single column, large targets, no hidden nav
Every control is visible without a hamburger menu or a swipe gesture to discover. Touch targets sit comfortably above 44px so this works one-handed, on the move.
tap to collapse
Desktop enhances. Mobile defines.
The desktop layout simply gives the same single-column flow more breathing room — it never introduces new structure mobile doesn't already have.

Screen 06 / 07 — Systems View

Architecture — the browser is enough

No backend, no timezone API, no server round-trip. Twine runs entirely in the browser, using data and APIs that already ship with every modern browser.

Why no backend exists
Timezone conversion is pure computation — given two cities and a date, the answer is deterministic. There's no reason to round-trip that to a server when the browser can compute it instantly and offline.
tap to collapse
Why no external APIs are required
Every modern browser already ships the Intl API and the full IANA timezone database. Calling out to a third-party timezone API would add latency, cost, and a dependency for something the platform already solved.
tap to collapse
The browser already provides everything necessary
This architecture is less a clever trick and more a refusal to add complexity that isn't earned. Fewer moving parts means fewer ways for Twine to ever feel unreliable.

Why beautiful tools can solve practical problems
A timezone calculator could be three dropdowns and a result. Making it feel warm doesn't change what it does — it changes whether people enjoy using it, and whether they trust the answer it gives them.
tap to collapse
Small utilities deserve thoughtful design
Most tools this small get built and forgotten. Twine treats a five-minute task with the same design care as a flagship product, because the size of a problem doesn't determine how much it deserves to be solved well.
tap to collapse
Removing complexity beats adding features
Every screen in this document could have grown a settings panel, a timezone-offset toggle, an advanced mode. Twine stays small on purpose — restraint was the hardest and most important design decision here.
